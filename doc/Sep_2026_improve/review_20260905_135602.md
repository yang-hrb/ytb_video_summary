# 仓库审阅：评价与改进意见

> 对象：`ytb_video_summary`（YouTube / Apple Podcast / 本地 MP3 → Whisper 转录 → OpenRouter 摘要 → 本地报告 + 可选 GitHub 备份）
> 审阅日期：2026-09-05
> 范围：`src/` 全量（约 4300 行）、`config/settings.py`、`tests/`（41 个）、`requirements.txt`、`web/`、`.gitignore`、`dashboard.sh`
> 方法：逐模块精读，以"可执行源码为准"，文档仅作交叉验证。

---

## 一、总体评价

这是一个**个人效率工具里完成度很高的项目**。核心链路（下载→转录→摘要→上传→落库）是闭环的，而且作者显然被真实失败毒打过——很多设计是"吃过亏"之后的样子：

| 亮点 | 说明 |
|---|---|
| 状态机 + Smart Resume | `ProcessingPipeline`（`src/pipeline.py`）+ `RunTracker.RESUMABLE_STATUS_MAP`（`src/run_tracker.py:272`），失败可从断点续跑，不用重下音频 |
| 幂等复用 | `find_latest_completed_report()`（`src/run_tracker.py:363`），COMPLETED 直接复用报告，playlist 重跑不浪费钱 |
| 双 Whisper 后端 | `src/transcriber.py`：Apple Silicon 走 `mlx-whisper`（Metal），其余走 `openai-whisper`，缺包自动降级 |
| OpenRouter 瀑布 | `src/summarizer.py:221`：3 个优先级模型 + fallback，每个模型 3 次指数退避，429/5xx 才换模型 |
| Cookie 策略 | `src/youtube_handler.py`：browser cookies 优先、`cookies.txt` 兜底，403/429/登录失效分级提示 |
| 动态 Prompt | `src/prompt_selector.py`：CSV（uploader→类型）+ 每类型多 prompt 随机抽 + `prompt_info` 落库可追溯 |
| 批处理预热 | `src/batch.py:19` `_make_shared_transcriber()`，一批视频只加载一次 Whisper 模型 |
| 失败日志治理 | 同一进程复用一个 `failures_{timestamp}.txt`（`src/run_tracker.py:377`），30 天自动清理，避免 80+ 碎文件 |
| Dashboard 闭环 | FastAPI（`src/dashboard_app.py`）+ `JobManager` + `ZipExporter`，可提 job、看统计、下 ZIP 包 |
| Watchlist + 日报 | `src/channel_watcher.py` + `src/daily_summary.py`，定时扫频道 + 每日 Markdown 聚合 |

**一句话结论：骨架正确、细节有债。** P0 级问题集中在四个地方：Config 单例、静默复用无逃生口、超长文本无截断、Dashboard 无鉴权。修完这四个，项目可用性上一个台阶；其余多为一致性、可观测性和工程化债。

## 二、高优先级问题（建议优先修）

### H1. `Config` 是"import 时快照"，测试改 env 不生效，且 import 副作用大

`config/settings.py:9-16`：所有 `os.getenv` 在类定义执行时（即 `import` 时）求值一次，之后改 `os.environ` 不再生效。`Config()` 构造时还顺手 `mkdir`（`:87-90`），意味着**任何 `import config`（包括测试 import）都会在磁盘建目录、且读到的是旧 env**。

附带问题：
- `HTTP_TIMEOUT = int(os.getenv(...))`（`:56`）写错 env 值会在 import 期直接抛 `ValueError`，堆栈难定位。
- `config.validate()`（`:74`）只校验 `OPENROUTER_API_KEY`，GitHub 配一半（有 TOKEN 无 REPO）要到上传时才暴露。
- `src/logger.py:setup_logging()` 在 `src/main.py:38` import 期执行，每次 import 新建一个 timestamped log 文件；`src/utils.py:10` 还有一份 `logging.basicConfig`，两者打架。

**建议**：改为实例属性惰性读取（或 `pydantic-settings`）；目录创建收敛到一个 `ensure_dirs()` 显式调用；`logger.setup_logging()` 只在 `main()` 入口调用一次，库 import 不产生文件副作用；`validate()` 拆成 `validate_for_run()` / `validate_for_upload()`。

### H2. "静默复用"没有逃生口，用户会以为程序坏了

`src/pipeline.py:199-207`（三处 run_* 都有）：identifier 命中 COMPLETED 报告即返回 `REUSED_EXISTING_REPORT`，**不重新下载、不重新摘要，且 CLI 无 `--force` 参数**（`src/cli/parser.py` 全文无 force/re-run）。想强制重跑只能手动删文件或改 DB，对普通用户不友好。

**建议**：加 `--force / --no-reuse` 透传到 pipeline；复用时打印报告路径 + 生成时间，让"跳过"可见。

### H3. `resume(DOWNLOAD_FAILED)` 实际上不可恢复，会空转

`src/pipeline.py:499-502`：`DOWNLOAD_FAILED → 'download'` 分支直接返回 `{'error': 'Must re-process...'}`，但 `DOWNLOAD_FAILED` 又在 `RESUMABLE_STATUS_MAP` 里，所以 `--resume-only` 每次都会捡起它、每次都失败。更糟的是**成功路径会删音频**（`run_youtube:241-243` 置 `audio_path_used=None` 并 `unlink`），于是 `TRANSCRIBE_FAILED` 的 resume（`:504-510` 依赖 `run.audio_path` 文件存在）也大概率降级为 `DOWNLOAD_FAILED`。

**建议**：二选一——(a) `get_resumable_runs()` 默认排除 `DOWNLOAD_FAILED`（需重下，单独命令处理）；或 (b) resume-download 分支真正重下（需要把 cookies/keep_audio 参数带进来）。同时 `KEEP_AUDIO=false` 时至少在 DB 记 `audio_deleted=true`，让用户知道为什么不能重转录。

### H4. 超长视频 transcript 直接拼进 prompt，无截断/分块，必撞 context 上限

`src/summarizer.py:200-206`：`transcript_clean` 全量拼进 prompt，`max_tokens=8000` 只限制输出。几小时的视频 transcript 可达几十万字符，OpenRouter 直接 400（context 超限），而 `_summarize_with_waterfall`（`:221`）对 400 归类为"非 retryable → 直接 raise"（`:248-249`），**连下一个模型都不试**。

**建议**：
1. 按字符/Token 上限截断（至少保命）；
2. 长期做 map-reduce：按段摘要再汇总（注意现有 prompt 里让模型"创建时间线"，分块后需保留时间偏移）；
3. waterfall 改为**收集每个模型的失败原因**，最后 `RuntimeError` 带上汇总（现在 `:254` 的 `"All OpenRouter models failed"` 无任何细节，排查全靠翻日志）；
4. 400 细分：`model_not_found / invalid_model` 应换下一个模型，只有鉴权类 401/403 才直接停。

### H5. Dashboard 无鉴权 + `api_key` 明文流转 + subprocess 调度脆弱

- `src/dashboard_app.py` 全接口无鉴权，`./dashboard.sh` 绑定 `127.0.0.1` 尚可，但一旦改成 `0.0.0.0` 即裸奔；`POST /api/jobs/playlist` 收 `api_key`（`:24-28`），经环境变量传给子进程，无掩码日志、无过期。
- `src/job_manager.py:62-85` 用 `subprocess.run(["python", "src/main.py", ...])`：依赖 CWD、调的是系统 `python` 而非 venv、无超时、无并发上限、无取消；`update_job(..., 'failed')` 丢弃异常堆栈（`:85` 连 `e` 都没记）。
- `app.mount("/static", ...web)`（`dashboard_app.py:22`）把整个 `web/` 对外暴露。

**建议**：至少加三件事——(a) dashboard 默认只听回环地址并在 README 明确警告；(b) `api_key` 只存内存/环境，不落库，job 记录脱敏；(c) 子进程改用 `sys.executable` + 绝对路径 + 超时 + job 取消接口；异常要进 `web_jobs.status=failed` 的错误字段。

### H6. `channel_watcher.execute_scan()` 有逻辑 bug + N+1 连接

`src/channel_watcher.py:125-136`：
```python
if not row or row[1] != 'COMPLETED':
    new_videos.append(vid)
elif vid == last_vid:
    break
```
`elif` 要求"row 存在且 COMPLETED 且等于 last_vid"才 break，但上面已把所有非 COMPLETED（含 FAILED）都加入 `new_videos`——FAILED 视频每次扫描都被重复处理，且 `break` 几乎走不到（entries 是按新到旧排，`reverse()` 后再逐个处理，顺序语义混乱）。另有：逐视频 `sqlite3.connect`（`:127` 在循环内，N+1）；`playlistend=15` 写死；`shared_transcriber = Transcriber()` 未 `load_model()` 预热（`:94`，与 batch.py 的做法不一致）；`last_seen_upload_date` 比较的是字符串日期，缺失时默认 `"00000000"` 脆弱。

**建议**：重写新视频判定（以 `last_seen_video_id` 为游标向上截断 + COMPLETED 去重，FAILED 单独列出不自动重跑）；连接复用一次；预热模型；`upload_date` 为空回退到 `published_parsed`。

### H7. `daily_summary` 读了不存在的列，时长恒为 0；uploader 靠文件名反推

`src/daily_summary.py:45`：`r.get('duration_seconds', 0)`——runs 表根本没有该列（见 `run_tracker.py:45-59` 建表语句），所以"总时长"永远是 `0h 0m 0s`。`uploader` 解析（`:88-104`）靠"文件名 split('_') 猜"，截断到 15/20 字符的标题一切就错位。

**建议**：runs 表加 `uploader`、`title`、`duration` 三列（pipeline `_complete` 时写入），daily digest 直接读列；这是小迁移、大回报。

## 三、中优先级问题（一致性与可观测性）

### M1. 数据库访问两套写法并存

`src/database.py:DatabaseManager`（WAL、`PRAGMA foreign_keys=ON`、`DatabaseError` 封装）是正道，但 `dashboard_service.py`、`job_manager.py`、`channel_watcher.py`、`daily_summary.py`、`zip_exporter.py` 全部直连 `sqlite3.connect`，**没有 WAL、没有外键、没有统一异常、超时行为不一致**。`DatabaseManager.begin_transaction()`（`database.py:153`）还是坏的（在新连接上 `BEGIN`，出了 `with` 即提交，毫无作用）。

**建议**：全仓收敛到 `DatabaseManager`；修掉或删掉 `begin_transaction`；dashboard 读多写少，加上读超时 `timeout=30`。

### M2. 状态字符串满天飞，无枚举

`'COMPLETED' / 'SUMMARIZE_FAILED' / 'SUMMARY_FAILED' / 'TRANSCRIPT_READY' / 'TRANSCRIPT_GENERATED'` 等散落在 pipeline、tracker、dashboard_service（`:18-20` 的 failed 求和漏了 `SUMMARY_FAILED` 和 legacy `failed`，统计口径与 `get_failed_runs` 不一致）、daily_summary（`:33` 的 `IN ('COMPLETED','REUSED_EXISTING_REPORT')`）。加一个新状态要改五处，必漏。

**建议**：一个 `RunStatus(str, Enum)` + `FAILED_STATUSES` / `RESUMABLE_MAP` 单一来源；`REUSED_EXISTING_REPORT` 到底算"完成"还是"跳过"，在统计、日报、ZIP 三处统一（现在各说各话）。

### M3. `BatchProcessor` 被写了却没被用

`src/batch_processor.py` 是漂亮的泛型批处理器，但 `src/batch.py` 四个批函数全是手写循环 + 手写 `_log_summary`，零复用。两套失败记录格式还不一样（`BatchResult.failures` vs `failed: List[tuple]`）。

**建议**：batch.py 迁移到 `BatchProcessor`，或删掉后者。留两套等于留两份 bug。

### M4. Prompt 随机不可复现 + 每次 new 开销

`src/prompt_selector.py:65` `random.randint` 无 seed，同 uploader 每次 prompt 可能不同，但 DB 只记 `prompt_index` 不记 prompt 全文——复现不了。`summarize_transcript`（`summarizer.py:314-319`）每次 `new PromptSelector + new Summarizer`，CSV 全量扫描 O(n)。且一旦命中 `custom_prompt`，`style/language` 参数被静默忽略（`:200-206`），调用方以为 `brief` 生效实际没有。

**建议**：prompt 全文（或 sha256）落库；允许 `--prompt-seed`；`Summarizer`/`PromptSelector` 做成可注入单例；文档写明"命中 uploader 定制 prompt 时 style 参数不生效"。

### M5. GitHub 备份策略会撑爆仓库

`upload_logs_to_github`（`github_handler.py:172`）把整个 `run_track.db`（二进制 SQLite，随使用增长）**直接 commit 进 git**，每次 `--upload` 还附带 daily digest + logs（`commands.py:293-319` 两个 `if upload` 可合并）。git 存大二进制 = 仓库体积单调增、clone 越来越慢。

**建议**：DB 改走 GitHub Release artifact（或只传 `VACUUM` 后的快照、限频如每天一次）；`_post_process` 合并为一次；`upload_to_github` 区分返回"未配置（None）"vs"上传失败（抛异常）"，现在一律吞成 None（`:167-169`），上层无法告警。

### M6. 日志系统 import 期副作用 + formatter 污染 record

- `main.py:38` import 期建 log 文件 → 跑单测 import 也会写 `logs/`（配合 `logger.handlers.clear()`（`logger.py:69`），重复 import 会丢 handler）。
- `ColoredConsoleFormatter.format`（`logger.py:28-33`）直接改 `record.levelname`，同一 record 进 file handler 时已带 ANSI 色码（实测 file 日志里常见 `\x1b[32m` 残留）。
- `utils.py:10-14` 的 `basicConfig` 与 `logger.py` 双重配置。

**建议**：`format` 里用局部变量着色不改 record；删掉 utils 的 basicConfig；`setup_logging` 幂等化（已有 handler 则直接返回）。

## 四、低优先级 / 代码细节

1. **`process_video` 默认值与 CLI 不一致**：`main.py:44` `cookies_from_browser=True`，而 `parser.py` 默认 `False`。直调函数与走 CLI 行为不同，会员视频一边能下一边 403。统一为 False 并显式传递。
2. **音频清理与 resume 互斥**（见 H3）：`KEEP_AUDIO=false` 时成功即删，失败残留 `temp/*.mp3` 无人清理；`temp/`、`output/transcripts`（现 65M）无配额/轮转。建议加 `--keep-audio` 按 run 保留 + 定时清理旧 transcripts。
3. **`sanitize_filename` 过于激进**（`utils.py:29`）：仅保留中英数字空格，连 `-_.` 都删，`create_report_filename` 再截断 uploader 15 / title 20 字符（`:172-176`），不同视频极易同名碰撞（后写覆盖前写）。建议保留 `-_.`、碰撞时缀 video_id。
4. **`download_subtitles` 只试 `zh,en`**（`youtube_handler.py:352`）；会员专属字幕语言可能是其他，建议可配置 `SUBTITLE_LANGS`。
5. **`transcriber.save_as_srt` 无防御**（`transcriber.py:170-176`）：`segment['start']` 缺键即 KeyError，建议 `.get` + 跳过坏 segment。
6. **`apple_podcasts_handler.download_audio` 无超时/重试**（`:249` `requests.get(stream=True)` 裸奔），大文件每 MB 打一条 INFO 日志刷屏。加 `timeout=config.HTTP_TIMEOUT` + 失败删半截文件。
7. **`get_category_folder` 回退表只有 12 个汉字**（`utils.py:81-106`），绝大多数中文首字走 `pypinyin`，没装时静默掉进 `00_number`。`pypinyin` 应为必装（现在 requirements 里是的，但代码仍按可选写，可简化）。
8. **`ZipExporter` 为 demo 逻辑**（`zip_exporter.py:24-36` 注释自己都写"for simplicity"）：job 无关联 run 时随手抓最近 10 个 COMPLETED 打包，用户下载的 ZIP 与 job 无关是大坑。`web_job_runs` 表已建好但**没有任何写入方**——先把写入补上再谈导出。
9. **`tests/test_dashboard.py` 是手写脚本不是单测**：硬编码 `venv/bin/uvicorn` + 固定端口 8080 + `time.sleep`，CI 必挂（已验证：41 测试中唯一 error 即它）。改为 `unittest` + `TestClient`（fastapi 自带）或标 `skipUnless`。
10. **工程化缺失**：无 `pytest`/`ruff`/`mypy` 配置、无 lockfile（requirements 全 `>=`，`yt-dlp` 这类快迭代包极易哪天 CI 挂）、无 CI workflow（`.github/workflows/` 为空目录）。建议 `pip-tools` 或 `uv` 锁版 + GitHub Actions 跑 `ruff + pytest（除 dashboard）`。
11. **`output/reports` 遗留目录**（现 5.9M）与现行 `output/summary` 并存，`.gitignore` 忽略整个 `output/`，新同学不知道哪个是真的。删 legacy 或 README 明确标注（本次已在 README/AGENTS 标注，待删除实体目录）。
12. **`HTTP_MAX_RETRIES=10` + `YOUTUBE_SLEEP` 默认偏大**，429 后重试 10 次可能卡几十分钟，建议降到 3-5 并在日志打印"第 N/M 次"。
